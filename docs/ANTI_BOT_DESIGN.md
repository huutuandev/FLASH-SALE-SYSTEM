# Anti-Bot Design & Fairness

In a flash sale, the biggest threat to fairness is automated bots and scripts that can send thousands of requests in the first few milliseconds, buying out the entire inventory before genuine human users can react.

## 1. Defense in Depth Strategy

We employ a multi-layered approach to filter out bots before they reach the core business logic.

### Layer 1: Edge / CDN (Cloudflare)
- **Web Application Firewall (WAF):** Blocks known bad IP addresses, malicious user agents, and anomalous request patterns.
- **Bot Fight Mode:** Cloudflare uses machine learning to identify and challenge (via CAPTCHA or JS challenge) suspected bot traffic.
- **Geo-Blocking:** If the flash sale is intended for a specific region, traffic from other countries can be blocked entirely at the edge.

### Layer 2: API Gateway / Rate Limiting
- **IP Rate Limiting:** Limit requests to a reasonable human threshold (e.g., 5 requests per second per IP).
- **User Rate Limiting:** If requests include an authorization token, limit requests per UserID.
- **Token Bucket / Leaky Bucket:** Allows a slight burst of traffic but strictly limits sustained traffic. Redis-based rate limiters are extremely fast and effective here.

### Layer 3: Application Level Anti-Bot
- **CAPTCHA / Proof of Work:** Before the flash sale starts, the client must compute a cryptographic hash or solve a hidden puzzle (like reCAPTCHA v3 or Turnstile). The resulting token is sent with the `POST /buy` request. Bots that try to bypass the UI won't have the valid token.
- **Dynamic Endpoints:** The actual URL or a required dynamic header for the flash sale (e.g., `/api/v1/buy?token=XYZ...`) is only revealed to authenticated, active websocket connections seconds before the sale starts.
- **Request Validation:** Strict validation of headers, requiring valid `Origin`, `Referer`, and custom encrypted headers generated by the official frontend app.

## 2. Preventing "Millisecond Botting"

Even if a bot bypasses the CDN and Gateway, it might send 1,000 requests in the very first millisecond of the sale.

**Solution: The Redis "One-Ticket" Rule**
Our Redis Lua script guarantees that no matter how many concurrent requests a single UserID sends, only the absolute *first* request to be processed by Redis will have a chance to reserve the item.
1. The script evaluates: `SISMEMBER flash_sale:item1:purchased_users {UserID}`.
2. If `true` (exists), the script aborts immediately.
3. If `false`, it adds the UserID to the set and decrements the stock.

This ensures **1 User = 1 Item maximum**, regardless of how many requests they fire simultaneously.

## 3. Account Farming Prevention

Bots often overcome the "One-Ticket" rule by creating thousands of fake accounts (Account Farming).
- **Solution:** Only accounts that meet certain trust criteria are eligible for the Flash Sale.
  - Must have a verified Phone Number (OTP).
  - Must be created > 30 days ago.
  - (Optional) Must have a history of previous successful purchases or a minimum account balance.
- **Implementation:** The UI only displays the Flash Sale button to eligible users. The backend API validates user eligibility during the token generation phase (minutes before the sale), *before* the extreme load hits the purchase endpoint, saving precious resources during the critical 100,000 req/sec spike.
